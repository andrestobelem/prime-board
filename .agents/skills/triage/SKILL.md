# Triage

Move issues on the project issue tracker through the triage role state machine.

If the repository treats external pull requests as a request surface (see the issue-tracker configuration), triage them too. **A PR is an issue with attached code**. Use the same roles, states, and state machine, with the differences marked "for a PR" below. Resolve a bare `#42` as an issue or PR according to the tracker configuration.

Every comment or issue posted during triage **must** start with this disclaimer:

```
> *This was generated by AI during triage.*
```

## Reference docs

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — how to write durable agent briefs
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) — how the `.out-of-scope/` knowledge base works

## Roles

Use two **category** roles:

- `bug` — something is broken
- `enhancement` — new feature or improvement

Use five **state** roles:

- `needs-triage` — maintainer needs to evaluate
- `needs-info` — waiting on reporter for more information
- `ready-for-agent` — fully specified, ready for an AFK agent
- `ready-for-human` — needs human implementation
- `wontfix` — will not be actioned

For a PR, apply the same states to the attached code. `ready-for-agent` means a brief is attached and an agent must take the next step on the diff. `ready-for-human` means a human can merge the PR.

Every triaged issue must have exactly one category role and one state role. If state roles conflict, report the conflict and ask the maintainer before continuing.

These are canonical role names. The issue tracker may use different label strings. Use the provided mapping. If no mapping exists, tell the user to run `/setup-matt-pocock-skills`.

State transitions: move an unlabeled issue to `needs-triage` first. From there, move it to `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`. Move `needs-info` back to `needs-triage` after the reporter replies. A maintainer can override any transition. Report unusual transitions and ask before proceeding.

## Invocation

The maintainer invokes `/triage` and describes the request in natural language. Interpret the request and act. Examples:

- "Show me anything that needs my attention"
- "Let's look at #42" (issue or PR)
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## Show what needs attention

Query the issue tracker and present three buckets in oldest-first order:

1. **Unlabeled** — never triaged.
2. **`needs-triage`** — evaluation in progress.
3. **`needs-info` with reporter activity since the last triage notes** — needs re-evaluation.

When PRs are in scope, include external PRs in these buckets and prefix each line with `[PR]` or `[issue]`. Discovery includes only *external* PRs, as defined by the tracker configuration. A collaborator's in-flight PR is not triage work. Apply this filter only to discovery. Always triage an explicitly named PR, regardless of its author.

Show counts and one-line summaries. Let the maintainer choose an item.

## Triage a specific issue or PR

1. **Gather context.** Read the full issue or PR (body, comments, labels, author, and dates; for a PR, read the diff too). Read prior triage notes so you do not repeat resolved questions. Explore the codebase with the project's domain glossary and respect ADRs in the area. Run two codebase checks: (a) **redundancy** — search for an existing implementation of the requested behavior by domain concept, not only by the request wording, and report where you searched. If found, classify the request as already implemented and use `wontfix` (step 5). (b) **prior rejection** — read `.out-of-scope/*.md` and report any similar record.

2. **Recommend.** Give the maintainer a category and state recommendation with reasons. Include a codebase summary relevant to the request and state whether the behavior already exists. Wait for direction.

3. **Verify the claim.** Before grilling, check the claim. For a bug, reproduce it from the reporter's steps. For a PR, confirm that the diff does what it claims. Check it out and run relevant tests or commands. Report the result as confirmed (with the code path), failed, or insufficient detail (a strong `needs-info` signal). A confirmed result improves the agent brief.

4. **Grill (if needed).** If the request needs more detail, call the Skill tool twice, for "grilling" and "domain-modeling". Ask one round of questions at a time. Sharpen domain terms and update `CONTEXT.md` or ADRs as decisions are made.

5. **Apply the outcome:**
   - `ready-for-agent` — post an agent brief comment ([AGENT-BRIEF.md](AGENT-BRIEF.md)).
   - `ready-for-human` — use the same structure as an agent brief. State why the work cannot be delegated (judgment calls, external access, design decisions, or manual testing).
   - `needs-info` — post triage notes (template below).
   - `wontfix` — close, with the comment depending on *why*:
     - **Already implemented** — the change already exists in the codebase. Point to where it lives; do **not** write to `.out-of-scope/` (that KB is for *rejected* requests, not built ones).
     - **Rejected (bug)** — polite explanation, then close.
     - **Rejected (enhancement)** — write to `.out-of-scope/`, link to it from a comment, then close ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - `needs-triage` — apply the role. Optional comment if there's partial progress.

## Quick state override

If the maintainer says "move #42 to ready-for-agent", trust the instruction and apply the role directly. Confirm the planned actions (role changes, comment, close), then act. Skip grilling. If moving to `ready-for-agent` without a grilling session, ask whether the maintainer wants an agent brief.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Record everything resolved during grilling under "established so far". Questions must be specific and actionable. Do not write only "please provide more info".

## Resuming a previous session

If prior triage notes exist, read them. Check whether the reporter answered outstanding questions. Present the updated state before continuing. Do not ask resolved questions again.
