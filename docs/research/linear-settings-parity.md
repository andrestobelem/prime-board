# Paridad de configuración: Linear y prime-board

**Fecha del relevamiento:** 2026-08-18
**Propósito:** comparar el alcance de la configuración pública de Linear con la configuración
visible hoy en `apps/web` de prime-board, priorizando los gaps que afectan a un board
API-first para agentes.

## Alcance y método

- Se consultó únicamente documentación de primera parte publicada en `linear.app/docs`,
  documentación de desarrolladores en `linear.app/developers` y el esquema GraphQL público
  enlazado por esa documentación en [Apollo Studio, esquema actual de Linear](https://studio.apollographql.com/public/Linear-API/schema/reference?variant=current).
  No se usaron comparativas, blogs ni documentación de terceros.
- La documentación de Linear usa _workspace_ para la organización raíz; el esquema GraphQL
  lo describe como `Organization`. La documentación de Developers identifica el endpoint
  público (`https://api.linear.app/graphql`) y que admite introspección: [GraphQL API —
  Getting started](https://linear.app/developers/graphql).
- El esquema se consultó el 2026-08-18 mediante introspección sin credenciales, verificando
  especialmente `Organization`, `Team`, `UserSettings`, `WorkflowState`, `IssueLabel`,
  `ViewPreferences` y `Webhook`, además de los nombres de las operaciones de consulta y
  mutación. El esquema puede cambiar; los enlaces anteriores son la fuente canónica vigente.
- Para prime-board se revisaron `SettingsView`, `TeamSettingsView`, `MembersView`, la
  navegación en `Sidebar`, `App` y `navigation`, y los módulos de tema y cliente GraphQL.
  Las referencias locales enlazadas son evidencia de la UI actual, no una afirmación de que
  el backend no tenga una capacidad no expuesta por estas vistas. No se hicieron cambios de
  código, tickets, commit ni push.

## Resumen ejecutivo

1. **La configuración actual de prime-board cubre un núcleo útil pero estrecho:** tema local,
   credencial de API, nombre del workspace, ciclo de vida de equipos, miembros/actores y
   claves, estados de workflow y labels. La página de team también permite membresías y
   muestra una vista de solo lectura cuando no se tienen permisos.
2. **Linear separa cuatro superficies que hoy están mezcladas o ausentes:** administración
   del workspace, configuración de cada team, preferencias de la cuenta y controles de
   seguridad/integraciones. Linear documenta además plantillas, ciclos, triage, vistas,
   notificaciones, auditoría, exportación y facturación.
3. **Prioridad P0:** hacer explícitos y aplicar en servidor los roles/permisos y el ciclo de
   vida de miembros/equipos, y dotar a las API keys de alcance revocable. Es la diferencia
   entre una UI de administración y una superficie segura para agentes.
4. **Prioridad P1:** persistir settings de team y cuenta, completar workflow/triage/ciclos,
   plantillas, notificaciones y webhooks. Son los controles que vuelven repetible y observable
   el trabajo automatizado.
5. **Prioridad P2/P3:** label groups y ciclo de vida de labels, vistas/preferencias avanzadas,
   proyectos/iniciativas, auditoría/exportación, SSO/SCIM/IP, integraciones generales y
   billing. SAML/SCIM, billing y features Enterprise de Linear son referencias de alcance,
   no requisitos del MVP de prime-board.

que soporta queries y mutations de entidades, y remite al schema explorer: [GraphQL API —

mostró una superficie de settings más amplia que la UI actual de prime-board:

## Propuesta priorizada de gaps

### P0 — seguridad y control operativo mínimo

1. **Modelo de autorización completo y consistente.** Separar workspace owner/admin/member,
   team owner/member y actor/agente; añadir guests solo si se necesitan. Hacer que el servidor
   sea la autoridad para workspace, team y operaciones sensibles, en vez de que la UI solo
   derive `canManage` de strings de rol. Aceptación de alto nivel: cada mutación de settings
   rechaza explícitamente un rol insuficiente y los mismos permisos aplican a UI y API.
2. **Invitaciones, suspensión y salida.** Incorporar invitaciones pendientes, aceptación,
   suspensión/revocación y membresías de team. El caso de uso de agentes requiere poder revocar
   un actor sin borrar su autoría histórica. La referencia de capacidades es [Invite members](https://linear.app/docs/invite-members)
   y [Members and roles](https://linear.app/docs/members-roles).
3. **API keys con alcance.** Mantener creación/revocación, pero agregar nombre, scopes mínimos,
   límite por team, rotación/expiración opcional, última utilización y revocación global. Nunca
   ampliar permisos por accidente al crear una key de agente. Linear documenta scopes y team
   limits en [API and Webhooks](https://linear.app/docs/api-and-webhooks).
4. **Visibilidad y acceso de teams.** Añadir al menos público/privado y una política clara de
   quién puede unirse; aplicar el filtro al API, navegación, asignaciones y webhooks. La
   motivación y las consecuencias de private teams están en [Private teams](https://linear.app/docs/private-teams).

### P1 — settings que hacen confiable el trabajo de agentes

5. **Persistencia de configuración por scope.** Crear superficies separadas para Workspace,
   Team y Account/User, con un origen server-side. Migrar tema, defaults de vistas y futuras
   preferencias desde `localStorage`, conservando un fallback local solo para onboarding.
6. **Workflow completo + triage.** Agregar descripción e invariantes de estados, default
   robusto, status Duplicate y settings de Triage (toggle, responsabilidad, reglas, prioridad
   requerida); después auto-close/auto-archive. Referencias: [Issue status](https://linear.app/docs/configuring-workflows)
   y [Triage](https://linear.app/docs/triage).
7. **Templates de issue y defaults.** Permitir templates de workspace/team con status, labels,
   prioridad, asignación y contexto inicial; luego formularios con campos requeridos. Esto reduce
   prompts ambiguos y trabajo de normalización posterior: [Issue templates](https://linear.app/docs/issue-templates).
8. **Notificaciones + webhooks.** Primero preferencias de Inbox y suscripciones; luego webhooks
   firmados por team/recurso para que agentes reaccionen a cambios sin polling. Referencias:
   [Notifications](https://linear.app/docs/notifications), [Webhooks](https://linear.app/developers/webhooks),
   [Rate limiting](https://linear.app/developers/rate-limiting).
9. **Team planning.** Añadir timezone, estimates y configuración de cycles (cadence, estado
   actual/futuros, rollover) en Team settings: [Cycles](https://linear.app/docs/use-cycles),
   [Estimates](https://linear.app/docs/estimates).
10. **Labels operables.** Descripción y archive/restore primero; grupos y merge después. Las
    descripciones son útiles para que una automatización o agente elija un label coherentemente:
    [Issue labels](https://linear.app/docs/labels).

### P2 — paridad de productividad y operación

11. **Vistas y defaults.** Hacer persistentes layout/group/order/columns, owner, scopes,
    suscripciones y defaults por usuario/workspace; mantener la navegación actual como índice.
    Referencias: [Custom Views](https://linear.app/docs/custom-views) y [Display options](https://linear.app/docs/display-options).
12. **Project/Initiative settings.** Lead, miembros/teams, status, fechas, milestones,
    dependencias, templates, notifications y toggles de initiatives: [Projects](https://linear.app/docs/projects),
    [Initiatives](https://linear.app/docs/initiatives).
13. **Audit log y exportación.** Registrar mutaciones administrativas, autenticación, keys y
    cambios de membresía; ofrecer CSV/JSON cuando exista una necesidad de backup o migración:
    [Audit log](https://linear.app/docs/audit-log), [Exporting Data](https://linear.app/docs/exporting-data).
14. **OAuth apps e integraciones seleccionadas.** La prioridad inicial debería ser un webhook
    seguro y un OAuth mínimo para agentes, no replicar todo el Integration Directory. Fuente:
    [OAuth2](https://linear.app/developers/oauth-2-0-authentication), [API and Webhooks](https://linear.app/docs/api-and-webhooks).
15. **Perfil y preferencias de cuenta.** Avatar/nombre/email, default home view, formatos de
    nombre, editor, desktop y code/review settings, si el producto deja de ser exclusivamente
    un cliente con API key: [Profile](https://linear.app/docs/profile), [Preferences](https://linear.app/docs/account-preferences),
    [Code & Reviews](https://linear.app/docs/code-and-reviews).

### P3 — enterprise o fuera del foco inicial

16. SAML/SCIM, dominios aprobados, login restrictions e IP allowlists: [Login methods](https://linear.app/docs/login-methods),
    [SAML](https://linear.app/docs/saml-and-access-control), [SCIM](https://linear.app/docs/scim).
17. Aprobación de aplicaciones de terceros, billing/planes y créditos de AI: [Third-Party App
    Approvals](https://linear.app/docs/third-party-application-approvals), [Billing and plans](https://linear.app/docs/billing-and-plans),
    [AI Credits](https://linear.app/docs/ai-credits).

## Decisión de alcance sugerida

Para la próxima etapa no conviene copiar el árbol de Settings de Linear de forma literal. La
secuencia recomendada es:

1. `Workspace`: roles, invitaciones/suspensión, API keys con scopes y acceso de teams.
2. `Team`: general (timezone/estimates), workflow/triage, labels, templates y cycles.
3. `Account`: preferencias persistentes, notificaciones y defaults de views.
4. `Integrations`: webhooks firmados y OAuth para agentes; conectores solo cuando exista un
   flujo concreto que los justifique.
5. `Audit/Export`: antes de habilitar administración multi-tenant o integraciones sensibles.
6. Enterprise/billing: explícitamente fuera del MVP hasta que cambie el modelo operativo.

El criterio rector es conservar la fortaleza de prime-board —agentes como actores de primera
clase y API-first— y tomar de Linear aquello que mejora **control, repetibilidad, seguridad y
observabilidad**, no todo su catálogo de configuración.
