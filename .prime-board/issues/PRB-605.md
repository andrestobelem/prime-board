# PostgreSQL: scopear Activity.actor y Query.actors por Workspace

Created by admin.

## Hallazgo

Durante la implementación de PRB-392 se detectó una posible fuga de aislamiento en la ruta PostgreSQL. `Activity.actor` usa `getPostgresActor` sin un scope de Workspace visible en el helper y `Query.actors` parece listar actores globales.

## Evidencia

- Ruta observada: resolución PostgreSQL de `Activity.actor` mediante `getPostgresActor` sin filtro de Workspace.
- Ruta observada: `Query.actors` consulta actores sin limitar el Workspace efectivo.
- El hallazgo requiere una matriz real con dos Workspaces y actores o Activities homónimos antes de corregirlo.

## Comportamiento esperado

Cada actor expuesto por Activity o por `Query.actors` debe estar autorizado dentro del Workspace efectivo. Un Actor global solo puede aparecer cuando existe una Membership válida en ese Workspace y la consulta no debe revelar membresías, IDs ni datos de otro Workspace.

## Criterios de aceptación

- [ ] `Activity.actor` resuelve con WorkspaceContext obligatorio y comprueba la Membership efectiva.
- [ ] `Query.actors` exige o deriva un Workspace efectivo y no devuelve actores de otro Workspace.
- [ ] Dos Workspaces con actores y Activities homónimos permanecen aislados en PostgreSQL.
- [ ] Se cubren API key, Actor compartido, Membership ausente/suspendida y selector falsificado.
- [ ] El contrato legacy conserva su comportamiento solo cuando existe un Workspace único y válido.
- [ ] Tests, typecheck, Prettier y diff-check pasan sin registrar secretos.

## Trazabilidad

Hallazgo descubierto durante PRB-392. No modificar este comportamiento desde PRB-392; este Issue debe investigarse y corregirse de forma independiente.
