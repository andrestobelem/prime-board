# CLI: alinear exit codes de recursos inexistentes con el contrato documentado

Created by admin.

## Hallazgo reproducible

La guía define exit code `1` para errores de API y `2` para errores de uso, pero varias consultas convierten un recurso inexistente en `UsageError`:

- `pb issue view PB-99`, `pb project view <missing>`, `pb cycle view <missing>`, `pb review view <missing>` e `initiative view <missing>` terminan con código 2.
- `resolveIssue/resolveTeam` y errores de mutations usan `ApiError` y terminan con código 1 para el mismo tipo de `NOT_FOUND`.

Evidencia: ramas `if (!data.*) throw new UsageError(...)` en `apps/cli/src/commands/issue.ts`, `project.ts`, `cycle.ts`, `review.ts` e `initiative.ts`; `docs/guia-agentes.md` documenta la semántica general. El comportamiento actual incluso queda codificado en un test de CLI, por lo que clientes deben conocer excepciones no documentadas.

## Comportamiento esperado

Un recurso inexistente debe producir una clasificación estable y consistente (`API error [NOT_FOUND]`, exit 1), mientras que sintaxis/flags inválidos producen exit 2.

## Criterios de aceptación

- Unificar `NOT_FOUND`, `UNAUTHORIZED` y errores GraphQL como exit 1 en todas las lecturas/mutaciones.
- Reservar exit 2 para usage/parseo.
- Actualizar tests y documentación; mantener mensajes legibles para agentes.
