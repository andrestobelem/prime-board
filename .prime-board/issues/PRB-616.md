# Web: descartar respuestas obsoletas al cambiar API key durante una request

Created by admin.

## Hallazgo

La revisión de PRB-382 encontró una carrera de credenciales en `apps/web/src/api.ts:gql`. La función no captura ni compara la API key usada para una request. Si otra pestaña cambia `pb.apiKey` mientras la request está pendiente, `credentialGeneration` puede no cambiar; cuando la selección de Workspace coincide o ambas son NULL, la respuesta vieja pasa las guardas y `setApiContext` guarda el Actor/Workspace anterior bajo la key nueva.

## Reproducción

1. Iniciar una request con actor/key A.
2. Cambiar `pb.apiKey` a key B antes de resolver el fetch.
3. Resolver la respuesta de A.
4. `getEffectiveWorkspaceContext()` conserva actor A y el marker queda como `credential(key-b)`.

La reproducción usa fake `localStorage`/`fetch`; no registra credenciales reales.

## Comportamiento esperado

Una respuesta debe aceptarse solo si corresponde a la credencial y generación vigentes de la request. Una respuesta obsoleta debe descartarse sin cambiar Actor, Workspace, cache ni `setApiContext`. El comportamiento debe ser consistente en `gql` y `useQuery`.

## Criterios de aceptación

- [ ] `gql` captura la API key/credencial y generación antes del fetch y las compara antes de aplicar contexto.
- [ ] `useQuery` conserva la misma protección en requests concurrentes.
- [ ] Cambios A→B con Workspace igual, distinto o NULL descartan respuestas viejas.
- [ ] La respuesta vigente de B actualiza solo el contexto/cache de B.
- [ ] Hay regresiones reproducibles sin secretos para requests concurrentes, cambio de key y cambio de Workspace.
- [ ] Typecheck, tests UI, Prettier y diff-check pasan o documentan fallos preexistentes.
