# Migrator: validar contrato completo de tablas Views legacy

Created by admin.

## Hallazgo

La revisión de PRB-620 reprodujo que `viewsMigrationSchemaProblems()` solo valida tablas, columnas, PK, nombres de índices y triggers. Una DB legacy con el `CHECK` de `view_preferences` eliminado y una fila `scope='actor'` con `actor_id=NULL` fue aceptada: `migrate()` registró 0032/0033 y conservó la fila inválida.

La misma ruta no valida CHECK/NOT NULL/defaults, FKs, UNIQUE ni filas de `saved_views`, `view_preferences` y `view_subscriptions`.

## Comportamiento esperado

La reconciliación legacy debe validar el contrato estructural y la integridad de datos de todas las tablas Views antes de registrar 0033. Un esquema o dato incompatible debe fallar cerrado sin DDL, pérdida de datos ni marker incorrecto.

## Criterios de aceptación

- [ ] CHECK, NOT NULL, defaults, PK, UNIQUE, FKs e índices requeridos se validan en las tres tablas Views.
- [ ] Filas incompatibles (por ejemplo actor scope sin actor_id o referencias rotas) fallan antes del marker.
- [ ] El fallo deja DDL, datos y `_migrations` sin cambios; el reintento repite el error.
- [ ] El esquema y los datos canónicos aplican 0033 y la repetición es idempotente.
- [ ] La validación no duplica la corrección de FK compuesta de PRB-629; usa un helper compartido cuando exista.
- [ ] Hay regresiones SQLite de fresh/legacy/fallo/reintento/rollback sin casts `as` nuevos.

## Trazabilidad

Hallazgo independiente durante la revisión de PRB-620. Corregir antes de integrar PRB-620/PRB-615.
