# GraphQL: rechazar referencias cross-Workspace en Initiatives

Created by Builder.

## Hallazgo reproducible

La revisión independiente de PRB-587 encontró un error de aislamiento en SQLite fuera del camino de API keys limitadas. Con dos Workspaces, un API key admin sin límite en el Workspace A puede ejecutar `initiativeCreate(projectIds: [projectIdDelWorkspaceB])`. `scope-dispatch` omite la comprobación para una key irrestricta y el dominio resuelve el Project sin `workspaceId`; la operación termina en `FOREIGN KEY constraint failed` en vez de devolver un error de dominio seguro.

## Comportamiento esperado

Una referencia a un Project de otro Workspace debe devolver `NOT_FOUND` o `UNAUTHORIZED`, no un error SQL interno. La mutación no debe crear la Initiative ni mezclar relaciones entre Workspaces.

## Evidencia

- Reproducción con `workspaceCreate` y un Project en Workspace B desde una sesión de A.
- Revisión independiente de PRB-587; no forma parte del bypass de API key limitada que se corrige en PRB-587.
- El camino afectado usa `getProject(db, projectId)` sin el `workspaceId` efectivo durante la creación de Initiative.

## Criterios de aceptación

- [ ] `initiativeCreate` y `initiativeUpdate` resuelven Projects y Teams dentro del Workspace efectivo.
- [ ] Una referencia cross-Workspace devuelve un error de dominio estable.
- [ ] No se persisten Initiative ni relaciones parciales después del rechazo.
- [ ] Hay una regresión real con dos Workspaces y referencias cruzadas.
- [ ] Se validan SQLite y, cuando exista URL, PostgreSQL.
