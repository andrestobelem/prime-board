# Inbox: conservar eventos derivados aunque cambie el assignee actual

Created by admin.

## Hallazgo reproducible

La relevancia de eventos derivados del inbox depende del assignee actual, no del estado cuando ocurrió el evento:

1. Asignar `PB-1` al actor A.
2. Como admin, cambiar el estado; el inbox de A muestra `state_changed` y `created`.
3. Antes de que A lea/archive el evento, desasignar el issue (`issueUpdate(assigneeId: null)`).
4. El inbox de A deja de mostrar `state_changed` aunque no existe receipt de lectura; solo queda `created`.

Evidencia: `listInboxActivity` filtra `state_changed`, `priority_changed` y `commented` usando el `i.assignee_id` actual. Un cambio posterior de asignación borra retroactivamente una notificación no leída.

## Comportamiento esperado

Una notificación derivada debe permanecer disponible hasta que el destinatario la lea/archive, o el contrato debe declarar explícitamente que el inbox representa relevancia viva y ofrecer otro historial para eventos no leídos.

## Criterios de aceptación

- Los eventos no leídos no desaparecen por cambios posteriores de assignee/estado/prioridad.
- Read/archive siguen siendo idempotentes y eliminan solo el evento solicitado.
- Definir comportamiento para desasignación y transferencia entre actores.
- Agregar regresiones con evento no leído antes y después de cambiar el assignee.
