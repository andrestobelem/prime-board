# Migración: la normalización legacy de Team Memberships no respeta Workspace

Created by admin.

## Hallazgo

La rama `scout/prb-472` (`58fbcc6`) agrega constraints y triggers que exigen `workspace_id` cuando existen varios Workspaces, pero el bloque final de `migrate()` conserva esta inserción legacy:

```sql
INSERT INTO team_memberships (id, team_id, actor_id, role, created_at)
VALUES (?1, ?2, ?3, 'owner', ?4)
```

El bloque recorre todos los Actors y todos los Teams cuando `team_memberships` está vacío. No envía `workspace_id` ni filtra la pertenencia del Actor al Workspace.

## Reproducción prevista

Una base con dos Workspaces, Actors y Teams, pero sin filas en `team_memberships`, ejecuta `migrate()` después de la migración de constraints. El trigger `team_memberships_workspace_required_insert` rechaza la escritura sin contexto. Si se desactiva el trigger, el producto crea memberships cross-Workspace.

## Comportamiento esperado

La normalización debe conservar el alcance de Workspace y crear solo memberships válidas para cada combinación Actor/Team permitida. No debe usar un producto cartesiano global.

## Criterios de aceptación

- [ ] La migración funciona con dos Workspaces y `team_memberships` vacío.
- [ ] Cada membership nueva tiene `workspace_id` correcto.
- [ ] No se crean memberships cross-Workspace.
- [ ] La prueba conserva la atomicidad si el backfill no puede resolver una pertenencia.
