# Replica: compatibilizar eventos históricos con workspaceId

Created by admin.

## Hallazgo reproducible

Después de integrar el scope por Workspace, `activityToDomainEvent` agrega `workspaceId` al envelope de eventos. El log canónico existente contiene eventos históricos con el mismo `eventId` y sin ese campo.

Al ejecutar un sync o una mutation sobre la base operativa, `EventLogWriter.appendMany()` compara el evento nuevo con el histórico y devuelve `EVENT_LOG_EVENT_ID_CONFLICT`, aunque la única diferencia sea el campo de alcance agregado por la migración.

**Evidencia:**

- Base operativa: 3754 filas de Activity.
- Log canónico válido antes del intento: 3747 eventos.
- Reproducción con `createRepoSync(db, repo).sync()` después de reiniciar el server con el código actual.
- Primer conflicto: `01a00a56-10da-7021-a4d7-9df65c13353b` (`AT-126`, `created`).
- El evento histórico no tiene `workspaceId`; el evento derivado de Activity sí.
- Esto bloquea comentarios y cambios de estado aunque la mutación SQLite pueda persistir.

## Comportamiento esperado

Una migración de alcance debe conservar eventos históricos y permitir nuevas mutations. Los eventos legacy sin `workspaceId` deben seguir siendo legibles, y un evento existente no debe producir conflicto solo por agregar el scope compatible. Los conflictos reales de payload deben continuar fallando.

## Criterios de aceptación

- [ ] El sync reconoce eventos legacy sin `workspaceId` sin duplicarlos ni perderlos.
- [ ] Los eventos nuevos incluyen el Workspace efectivo.
- [ ] Un cambio real del payload con el mismo `eventId` sigue produciendo conflicto.
- [ ] Las mutations GraphQL/CLI vuelven a responder y la réplica se actualiza.
- [ ] Existe una regresión de migración legacy → scoped.
- [ ] Focales, typecheck, Prettier y `git diff --check` pasan.
