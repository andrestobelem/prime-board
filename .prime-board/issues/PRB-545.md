# PostgreSQL: migrar Documents al backend async

Created by admin.

## Objetivo
Migrar Documents del backend SQLite al backend PostgreSQL objetivo. Documents no puede quedar limitado a SQLite durante el cutover.

## Evidencia
- `apps/server/src/graphql/document-resolvers.ts` ya enruta Documents a la implementación async cuando existe `context.persistence`.
- PostgreSQL es el backend objetivo del proyecto.
- `PRB-541` entregó el modelo y las superficies agent-first, pero dejó este hueco de backend.

## Alcance
- Añadir la migración PostgreSQL de `documents`, sus índices y las FKs necesarias.
- Crear dominio PostgreSQL para listar, consultar, crear, editar, archivar y restaurar Documents.
- Mantener los vínculos a Issue, Project, Team, Initiative y Cycle.
- Aplicar permisos, WorkspaceContext, scopes de API keys y límites de Team igual que en SQLite.
- Hacer que GraphQL, CLI, MCP y los resolvers anidados funcionen con PostgreSQL.
- Añadir pruebas de integración PostgreSQL y conservar las pruebas SQLite.
- Actualizar la documentación para retirar la limitación cuando la migración esté completa.

## Criterios de aceptación
- [x] `migratePostgres` crea `documents` de forma idempotente.
- [x] CRUD, búsqueda, archivo y restauración funcionan contra PostgreSQL.
- [x] Un Document puede vincularse a como máximo un recurso.
- [x] Una API key limitada no puede leer ni escribir Documents fuera de sus Teams.
- [x] No queda un fallback de escritura a SQLite para Documents.
- [x] Pasa el harness PostgreSQL y las suites SQLite relevantes.

## Fuera de alcance
Version history, comentarios inline, templates, suscripciones, adjuntos ricos y colaboración en tiempo real.
