# Punto único de despacho para sincronizar el repo tras una mutación (expand)

De docs/adr/0004-repo-como-fuente-de-verdad.md: SQLite es un índice descartable, el repo queda al día en cada mutación. Hoy esa garantía depende de que cada resolver llame a mano a context.repo?.sync() o syncIssue(id) — 22 de las 26 mutations del schema lo hacen, repetido en 3 archivos (resolvers.ts, issue-resolvers.ts, project-resolvers.ts). Las 4 que correctamente NO sincronizan (apiKeyCreate, apiKeyDelete, webhookCreate, webhookDelete) lo hacen por disciplina de quien escribió el resolver, no por una regla estructural — nada avisa si una mutación nueva se olvida la línea.

## What to build
Un mecanismo que decida automáticamente si sincronizar el repo después de una mutación (envolviendo el resolver map de Mutation, o vía el ciclo de vida de graphql-yoga), con las 4 exclusiones de secretos declaradas explícitamente por nombre. Este ticket es el "expand": convive con las llamadas manuales existentes sin quitarlas todavía — sync() es idempotente, así que la duplicación momentánea es inofensiva.

## Acceptance criteria
- [ ] El mecanismo dispara sync()/syncIssue() automáticamente en al menos una mutación de prueba, sin que el resolver lo llame a mano
- [ ] apiKeyCreate, apiKeyDelete, webhookCreate y webhookDelete quedan excluidos por nombre, no por omisión
- [ ] bun test sigue en verde con las llamadas manuales todavía presentes
