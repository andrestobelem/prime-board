# Replica: evitar reescaneo cuadrático del event log en cada cambio

Created by admin.

## Hallazgo reproducible

Cualquier mutation que no llama a `sync()` o `syncIssue()` entra en el fallback de `withRepoSyncDispatch` y ejecuta un sync completo de la réplica. Con el event log actual, ese camino vuelve a leer el log completo para cada evento histórico.

## Evidencia

- SQLite operativo: `3,555` filas en `activity`.
- Event log: `3,555` líneas y `2,101,666` bytes.
- En una copia aislada de la base, `createRepoSync.sync()` no terminó en 20 segundos y consumió CPU de forma sostenida.
- `EventLogWriter.appendMany()` valida todos los eventos y llama a `append()` por cada uno; `append()` vuelve a leer y parsear el log completo.
- El problema aparece después de la escritura SQLite, durante la sincronización del Repository Replica.

## Comportamiento esperado

Una mutation normal debe responder en tiempo acotado aunque el event log sea grande. El sync debe leer el log actual una vez y procesar solo eventos nuevos. La idempotencia, el orden y la protección contra conflictos deben mantenerse.

## Criterios de aceptación

- [ ] Un sync idempotente con miles de eventos no reparsea el log completo por cada evento.
- [ ] Una mutation normal responde en tiempo acotado con el event log actual.
- [ ] Los eventos nuevos se agregan en orden y los duplicados no se escriben.
- [ ] Un conflicto de `eventId` conserva el error actual.
- [ ] Existe una regresión de rendimiento o de llamadas de lectura que evita el comportamiento O(n²).
- [ ] Pasan tests focales, typecheck, Prettier y `git diff --check`.

## Relaciones

- Relacionado con `PRB-566`: corrige `ENOBUFS` al leer un event log grande.
- Relacionado con `PRB-568`: excluye recibos personales del sync; este Issue cubre el camino general.
