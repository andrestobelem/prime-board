# Clientes GraphQL: hacer seguro el fallback legacy y la detección concurrente

Created by admin.

## Hallazgo de revisión independiente de PRB-479

Los adaptadores de clientes tienen dos defectos de robustez:

1. CLI y MCP usan una única promesa global `detectingContract`. Requests concurrentes para distintos endpoints o credenciales pueden compartir el resultado de introspección equivocado. El segundo endpoint no se sondea y puede recibir campos `workspaceId` o `X-Workspace-ID` incompatibles.
2. `withoutWorkspaceFields()` elimina `workspaceId` con regex. En una operación GraphQL legacy puede dejar variables no usadas, alias sin selección o argumentos inválidos. Ejemplos: `query($workspaceId: ID!) { viewer { id workspaceId } }`, `{ w: workspaceId }`, `{ thing(workspaceId: $id) }`.

## Comportamiento esperado

Cada endpoint/credencial debe tener una detección aislada y concurrente segura. El fallback legacy debe quitar solo selecciones/argumentos soportados con una transformación GraphQL válida, conservar una operación válida y limpiar variables no usadas, o usar documentos legacy explícitos.

## Criterios de aceptación

- [ ] CLI y MCP aíslan cache e introspección en vuelo por endpoint y credencial.
- [ ] Hay regresiones concurrentes para dos endpoints con contratos distintos.
- [ ] El fallback legacy conserva sintaxis válida en selecciones, aliases, argumentos, variables y directivas.
- [ ] Las requests modernas conservan campos y header.
- [ ] Focales, typecheck, build, Prettier y diff-check pasan.
