# Planning: completar ACL y Team limits en dependencies y status updates

Created by admin.

## Hallazgo

Las mutaciones de relaciones y updates de planning no aplican la misma ACL y los límites de Teams de una API key en todos los backends. `projectDependencyCreate` PostgreSQL valida el límite del Project origen, pero no aplica la autorización de gestión para el origen/destino ni valida explícitamente tipo/self-reference. `initiativeStatusUpdateCreate/Delete` debe aplicar ACL de Initiative y `apiKeyTeamsWithinLimit` antes de escribir o borrar.

## Comportamiento esperado

Una operación de dependency o status update debe fallar cerrado si el actor no puede administrar el recurso, si el destino está fuera del alcance o si la API key está limitada a otros Teams. La validación debe ocurrir antes de INSERT/DELETE y ser equivalente en SQLite/PostgreSQL. Los errores no deben revelar la existencia de recursos ajenos.

## Criterios de aceptación

- [ ] Project dependency create/delete valida ACL de origen y destino, Team limits, tipo, self-reference y Workspace.
- [ ] Initiative status update create/delete valida ACL owner/team y Team limits antes de escribir.
- [ ] API key limitada recibe el mismo error estable en SQLite y PostgreSQL.
- [ ] Regresiones prueban outsider, owner/team member, admin, key limitada, destino ajeno y rollback sin escrituras parciales.
- [ ] No se filtran filas ni IDs de otros Workspaces.
