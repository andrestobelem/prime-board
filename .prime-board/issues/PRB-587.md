# GraphQL: conservar la semántica de listas vacías en referencias scoped

Created by Builder.

## Hallazgo reproducible

La resolución de alcance convierte una lista explícita vacía en `__missing__` mediante `ids([])`. Esto cambia la semántica de dominio de las mutaciones: una lista vacía puede responder `NOT_FOUND` o `UNAUTHORIZED` en vez de conservar la validación esperada para una entrada vacía. La inconsistencia también aparece entre SQLite y PostgreSQL en operaciones de proyectos e iniciativas.

## Evidencia

- `apps/server/src/auth/scope-dispatch.ts:148-153, 253-267, 676-679`.
- Revisión independiente de `66935eb`: una API key limitada falla contra iniciativas válidas relacionadas solo con el proyecto cuando recibe una lista vacía.
- Las integraciones PostgreSQL existen, pero no se ejecutaron porque `PRIME_BOARD_POSTGRES_URL` no está configurado.

## Comportamiento esperado

Una lista vacía explícita debe conservar la validación de dominio (`VALIDATION_FAILED` cuando corresponda). Una referencia inexistente debe continuar fallando cerrado como `NOT_FOUND`. La semántica debe ser consistente entre SQLite y PostgreSQL.

## Criterios de aceptación

- [ ] `ids([])` no se confunde con una referencia inexistente.
- [ ] Las mutaciones de proyectos e iniciativas devuelven el error de validación definido para listas vacías.
- [ ] Las referencias inexistentes siguen devolviendo `NOT_FOUND` y nunca autorizan.
- [ ] Hay regresiones SQLite y PostgreSQL para lista vacía, referencia inexistente, referencia ajena y referencia permitida.
- [ ] La integración PostgreSQL se ejecuta con una URL real o queda documentada como brecha de validación.
