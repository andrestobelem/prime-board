# Inbox: no crear receipts huérfanos cuando mark-read/archive falla

Created by admin.

## Hallazgo reproducible

`inboxMarkRead` y `inboxArchive` dejan una escritura aunque la actividad no sea una entrada del inbox del actor:

1. Obtener el `activity.id` de un issue ajeno/no relevante para un actor autenticado.
2. Ejecutar `inboxMarkRead(id: <activityId>)` (o `inboxArchive`) con ese actor.
3. La API responde `NOT_FOUND: Inbox item not found`, pero `inbox_receipts` ya contiene una fila para `(activity_id, actor_id)` y puede quedar `read_at/archived_at` persistido.

Evidencia: `apps/server/src/domain/inbox.ts:ensureReceipt` inserta el receipt antes de llamar a `listInboxActivity`; si la actividad no es relevante, `markInboxRead/archiveInboxItem` lanza después sin rollback. El mismo patrón falla para entradas que quedan fuera del límite hardcoded de 100.

## Comportamiento esperado

Una operación rechazada no debe modificar receipts ni cualquier otro estado. La relevancia y pertenencia al inbox deben validarse antes de insertar, o la inserción y validación deben ejecutarse atómicamente.

## Criterios de aceptación

- `NOT_FOUND` por actividad ajena, archivada/no visible o fuera de página no deja filas ni timestamps.
- Read/archive válidos siguen siendo idempotentes y persisten su receipt.
- El límite de consulta no convierte una entrada válida en un falso `NOT_FOUND`.
- Regresiones verifican estado de DB antes y después del rechazo.
