# Auth: definir ownership y permisos de webhooks

Created by admin.

## Hallazgo reproducible

Los webhooks no tienen propietario ni permisos asociados. `webhookCreate` y `webhookDelete` solo llaman `requireViewer`, así que cualquier actor autenticado puede borrar la suscripción creada por otro actor. En una reproducción aislada, un agent outsider creó una API key propia y eliminó con éxito el webhook creado por `admin`.

## Evidencia

- `apps/server/src/graphql/resolvers.ts`: `webhookCreate` y `webhookDelete` no consultan workspace role, owner ni membership.
- `apps/server/src/db/migrations/0001_init.sql`: `webhooks` no tiene `owner_id`.
- Reproducción con `createTestApp`: `webhookDelete` devuelve `success: true` usando la key de un actor diferente.

## Comportamiento esperado

La API debe definir si los webhooks son recursos del workspace (solo admin) o recursos del actor (owner y admin), persistir esa propiedad y rechazar operaciones de terceros.

## Criterios de aceptación

- [ ] Se documenta la política de ownership/visibilidad de webhooks.
- [ ] Un actor no autorizado no puede borrar ni manipular suscripciones ajenas.
- [ ] `webhooks` lista solo los recursos visibles según esa política.
- [ ] Migración y pruebas cubren datos existentes sin exponer secretos.
