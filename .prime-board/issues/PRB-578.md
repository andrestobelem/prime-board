# GraphQL: cerrar side-channel en mutaciones análogas scoped

Created by admin.

## Hallazgo de revisión de PRB-576/PRB-577

Persisten mutaciones SQLite que ejecutan autorización sobre IDs sin WorkspaceContext antes de resolver el recurso. Esto crea un side-channel: para el mismo Team/Project de otro Workspace, un admin recibe `NOT_FOUND` después del guard y un member recibe `UNAUTHORIZED` antes del guard.

Rutas confirmadas por probe dinámico con dos Workspaces:

- `teamArchive`, `teamUnarchive`, `teamDelete` (`assertWorkspaceAdmin` antes de `requireTeam`).
- `projectCreate` (`assertCanCreateProject` antes de `requireTeam`).
- `projectArchive`, `projectUnarchive` (`assertCanManageProject` antes de `requireProject`).
- `projectUpdate` al reemplazar `teamIds` (`assertCanManageProjectTeams` antes de `requireTeam`).
- `milestoneCreate` (`assertCanManageProject` antes de `requireProject`).
- `savedViewCreate` (`assertCanManageIssue` antes de resolver el Team/Issue scoped).

PRB-577 corrigió teamUpdate, labelCreate, workflowStateCreate y cycleCreate, pero no todas estas rutas análogas.

## Comportamiento esperado

Toda mutación debe resolver primero su recurso bajo el Workspace efectivo. Un ID cross-Workspace debe devolver `NOT_FOUND` de forma consistente para admin y member, sin ejecutar una autorización que revele la existencia del recurso.

## Criterios de aceptación

- [ ] Las rutas confirmadas resuelven primero Team, Project, Issue o recurso padre scoped.
- [ ] Admin y member reciben `NOT_FOUND` para IDs de otro Workspace.
- [ ] Las operaciones válidas conservan su autorización y respuesta.
- [ ] Existe una regresión para las rutas análogas.
- [ ] Focales, typecheck, build, Prettier y diff-check pasan.
