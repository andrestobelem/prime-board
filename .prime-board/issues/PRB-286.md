# UI: completar estados de carga, error, vacío y paginación

Created by admin.

## Contexto
La auditoría PRB-278 detectó que el shell y las vistas dejan al usuario sin recuperación clara ante errores y truncan colecciones a 250 elementos. Los estados vacíos tampoco distinguen ausencia de datos de filtros sin coincidencias.

## Evidencia
- `apps/web/src/App.tsx` monta sidebar vacío mientras carga `SHELL_QUERY` y muestra error sin Retry.
- `apps/web/src/components/IssueList.tsx` solo muestra los primeros 250 y recomienda estrechar filtros.
- `TeamView.tsx`, `BoardView.tsx` y `ProjectView.tsx` fijan `first: 250`; Board/Project no comparten el toolbar de filtros.
- `IssueList.tsx`, `TeamsView.tsx` y `ProjectsView.tsx` muestran empty states genéricos sin CTA contextual.

## Comportamiento esperado
Toda vista tiene un camino visible para cargar, recuperarse de un error y empezar a trabajar; las listas pueden recorrer más de 250 resultados sin perder issues.

## Criterios de aceptación
- [ ] Crear un patrón común `Loading / Error + Retry / Empty + CTA` para shell y vistas principales.
- [ ] Implementar cursor/load-more o paginación para issues y conservar `pageInfo` en lista, board, project e issue navigation.
- [ ] Reutilizar filtros/búsqueda/selección en Board y Project, o documentar una excepción explícita.
- [ ] Diferenciar “no hay datos” de “ningún resultado coincide” y ofrecer Clear filters cuando corresponda.
- [ ] Agregar CTA visible `New issue` y acciones de creación relevantes en Teams/Projects sin depender solo de `C`/`Cmd+K`.
- [ ] Cubrir un caso con más de 250 issues y errores recuperables en tests/integración.
