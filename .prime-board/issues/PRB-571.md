# Tracker: serializar repo sync para evitar eventos canónicos inesperados

Created by admin.

## Hallazgo reproducible

Con varias escrituras GraphQL/CLI concurrentes, la API aplica el cambio pero el CLI termina con:

`Canonical event log contains an unexpected event: <eventId>`

El fallo apareció al reclamar tickets en paralelo. `issue view` confirmó que el estado y el assignee sí quedaron aplicados. El mismo evento fue observado por varios workers.

## Evidencia

- Ocurrió durante claims concurrentes de `PRB-383`, `PRB-461` y otros tickets.
- `PRB-568` y `PRB-569` también registraron el mismo error después de que sus comentarios/estados sí persistieran.
- El runtime sigue respondiendo `/health` con `200`.
- Los workers dejaron de escribir al tracker para evitar más carreras.

## Comportamiento esperado

Una mutation debe devolver éxito solo cuando termina su sincronización, o debe devolver un error recuperable y determinista sin dejar una respuesta ambigua. Las escrituras concurrentes no deben producir eventos inesperados ni invalidar el checkpoint del repo sync.

## Criterios de aceptación

- [ ] Una reproducción concurrente de dos o más mutations falla antes del fix y pasa después.
- [ ] El repo sync serializa o coordina writers y checkpoints sin perder eventos.
- [ ] Una respuesta de error no oculta si la mutation ya persistió; el retry es idempotente.
- [ ] El event log conserva orden, deduplicación y detección de conflictos.
- [ ] Existe una regresión focal sin mutar el checkout del test que la invoca.
- [ ] Pasan tests focales, typecheck, Prettier y `git diff --check`.

## Alcance

Este ticket cubre el error de concurrencia del sync. `PRB-567` cubre el aislamiento de fixtures Git y no se duplica aquí.
