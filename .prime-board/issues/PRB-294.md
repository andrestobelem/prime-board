# Saved Views: aplicar ACL de membership a vistas con scope de team

Created by admin.

## Hallazgo reproducible

Las vistas guardadas de team ignoran membership:

1. Admin crea `savedViewCreate(input: { name: "PB private", scope: TEAM, teamId: <PB> })`.
2. Un actor con API key válida pero sin membership en `PB` ejecuta `savedViews(teamId: <PB>)` y ve la vista.
3. El mismo outsider puede ejecutar `savedViewUpdate(id: <viewId>, input: { name: "renamed" })` y `savedViewDelete(id: <viewId>)` con éxito.
4. También puede crear otra vista `scope: TEAM` apuntando a `PB`, aunque luego no debería ser visible para él.

Evidencia: `apps/server/src/domain/saved-views.ts:57-62` devuelve `true` para cualquier scope no personal; `apps/server/src/graphql/resolvers.ts:598-643` no aplica `assertCanManageTeam` ni una política equivalente.

## Comportamiento esperado

Una vista con scope `TEAM` debe ser visible y mutable según la membership/política del team. Un outsider debe recibir `NOT_FOUND` o `UNAUTHORIZED`, no leer, editar, borrar ni crear recursos team-scoped ajenos. Las vistas workspace/personal deben conservar sus reglas actuales.

## Criterios de aceptación

- Cubrir owner/member/admin y outsider para list/get/create/update/duplicate/delete/archive.
- Revocar membership elimina inmediatamente el acceso de la key existente.
- No se crean vistas team-scoped inaccesibles o huérfanas por actores no autorizados.
- Documentar la matriz de permisos y agregar regresiones GraphQL/CLI/MCP.
