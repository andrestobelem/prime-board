# Cycles: rechazar ajustes de fechas pasadas en UPCOMING

Created by Micaela.

## Hallazgo reproducible

La revisión de `PRB-388` sobre `81fb5165bb57870ca5c9e5972b96f3f502a51f2f` detectó que `cycleUpdate` permite editar las fechas de un ciclo `UPCOMING` que ya está en el pasado.

## Evidencia

`updateCycle` en `apps/server/src/domain/cycles.ts` (alrededor de las líneas 337–346) solo comprueba `existing.state === "upcoming"` para permitir el cambio de fechas. PostgreSQL mantiene la misma condición en `apps/server/src/domain/postgres-cycles.ts`.

Reproducción SQLite GraphQL: crear un ciclo UPCOMING futuro y actualizarlo con `startsAt: "2000-01-01"` y `endsAt: "2000-01-07"`. La mutación se acepta y devuelve el ciclo UPCOMING, con `cadenceSource: MANUAL`, aunque la fecha ya pasó. El mismo caso debe verificarse en PostgreSQL.

## Comportamiento esperado

Las fechas pasadas de un ciclo no se pueden cambiar. Solo un ciclo futuro puede ajustarse manualmente; si la actualización convertiría el ciclo en pasado, debe rechazarse con un error de validación. Una operación rechazada no debe cambiar fechas, `cadenceSource` ni el horizonte.

Fuente: `https://linear.app/docs/use-cycles` ("Past cycle dates cannot be changed").

## Criterios de aceptación

- [ ] SQLite y PostgreSQL rechazan cambios a fechas pasadas para ciclos futuros.
- [ ] La validación temporal usa el instante actual y se aplica si cambia `startsAt` o `endsAt`.
- [ ] Un rechazo no marca el ciclo MANUAL ni consume `cycleUpcomingCount`.
- [ ] Existen regresiones para fecha pasada, fecha futura válida y ciclo ya iniciado/completado.
- [ ] La API conserva la distinción MANUAL solo para ajustes futuros válidos y permite rollback transaccional ante error.
