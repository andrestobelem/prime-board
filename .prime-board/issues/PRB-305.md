# Rebuild: rechazar colisiones de nombres de proyectos antes de reasignar issues

Created by admin.

## Hallazgo reproducible

Dos proyectos del mismo team pueden tener el mismo nombre, pero export/import usa ese nombre como clave:

1. Crear proyectos `Same` y `Same` en `PB`.
2. Crear `PB-1` asociado al primero y `PB-2` al segundo.
3. Exportar y reconstruir en una DB limpia.
4. Ambos issues terminan asociados al proyecto reconstruido que se procesó último; se pierde la relación original sin error.

Evidencia: `apps/server/src/export/importer.ts` construye `projectIds` por `project.name`; las referencias de issues, milestones, updates e iniciativas se resuelven con esa tabla. El modelo no impone nombre único y el exporter no rechaza esta ambigüedad.

## Comportamiento esperado

El round-trip debe conservar ownership aunque haya nombres iguales, usando una identidad estable/composite o rechazando la ambigüedad antes de borrar la DB. Nunca debe reasignar silenciosamente issues.

## Criterios de aceptación

- Dos proyectos homónimos conservan sus issues, milestones, updates e iniciativas tras export/rebuild.
- Colisiones entre snapshots producen un diagnóstico accionable antes de modificar la DB.
- La estrategia se documenta y se aplica también a referencias parciales.
- Agregar regresiones de round-trip con proyectos homónimos.
