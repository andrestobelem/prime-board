# Arquitectura: cerrar el contrato de Workspace, Actor y selección segura

Created by admin.

## Objetivo
Convertir las decisiones de la épica en un contrato implementable y actualizar el modelo de dominio antes de modificar el esquema.

## Alcance
- Registrar un ADR que sustituya la premisa singleton: una DB/proceso contiene varios Workspaces aislados.
- Fijar `Actor` como identidad global y `Workspace Membership` como relación con `role` (`admin`/`member`) y `status` (`active`/`suspended`/`left`). El `workspace_role`/status actual queda como compatibilidad transitoria y luego se retira.
- Fijar API keys globales del Actor con grants por Workspace; scopes (`read`/`write`/`admin`) y allowlists de Teams se evalúan en el Workspace efectivo. Una key legacy recibe un grant al Workspace existente.
- Fijar la selección mediante `WorkspaceContext` resuelto por key + `X-Workspace-ID` validado, perfil/sesión o default persistido; el selector jamás otorga acceso. Definir error cuando no hay contexto resoluble.
- Fijar unicidad: `urlKey` global; Team `key` por Workspace; número de Issue por Team; referencias legibles se resuelven siempre dentro del contexto.
- Fijar que no se implementan OAuth/SSO/SCIM, billing, hosted multi-tenant ni borrado irreversible en esta épica.

## Criterios de aceptación
- [ ] ADR y `CONTEXT.md` describen entidades, invariantes, selección, compatibilidad y no-objetivos.
- [ ] Existe un diagrama/lista de tablas y relaciones que los tickets de datos pueden ejecutar sin decisiones abiertas.
- [ ] Se documentan los códigos de error y la compatibilidad de requests legacy sin header cuando la key tiene un único/default Workspace.
- [ ] El ADR-0003 queda revisado o enlaza explícitamente al nuevo ADR; no queda documentación que prometa singleton después de habilitar la feature.
