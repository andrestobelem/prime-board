# Modelo y API: persistir favoritos por Actor

Created by admin.

## Hallazgo reproducible

La referencia muestra una sección `Favorites` con proyectos destacados por el usuario (por ejemplo, `BizaClaw`). prime-board no tiene entidad ni relación persistida para favoritos; el sidebar tampoco puede reconstruir esa lista desde GraphQL.

## Evidencia

- La captura muestra `Favorites` entre los recursos del workspace y los teams.
- `apps/server/src/db/migrations/0001_init.sql` y migraciones posteriores no contienen favoritos.
- `apps/web/src/components/Sidebar.tsx` recibe workspace, teams, projects, cycles, views e initiatives, pero no favoritos.
- `Actor` identifica al viewer y `Project`/`SavedView` ya existen; el faltante es la relación ordenada por actor.

## Comportamiento esperado

Cada Actor debe poder agregar/quitar favoritos y conservar un orden estable. El favorito debe ser privado del actor y no alterar el scope ni la visibilidad del recurso original.

## Criterios de aceptación

- [ ] Se define una relación persistida de favoritos con owner `actor_id`, recurso soportado y posición/orden.
- [ ] La relación mantiene integridad referencial y rechaza duplicados; borrar o archivar el recurso no deja favoritos huérfanos.
- [ ] GraphQL expone favoritos del viewer y mutations idempotentes para agregar, quitar y reordenar.
- [ ] La autorización impide leer o modificar favoritos de otro actor.
- [ ] Export/rebuild preserva favoritos sin incluir secretos.
- [ ] Hay regresiones para dos actores con favoritos distintos y para proyectos/vistas archivados.
