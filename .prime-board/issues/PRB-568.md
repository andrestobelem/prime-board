# Inbox: evitar bloqueo al marcar una entrada como leída

Created by admin.

## Hallazgo reproducible

En Inbox, al pulsar `Mark read`, la entrada queda en `Marking…` y la mutación GraphQL `inboxMarkRead` no devuelve respuesta. Durante la espera, las operaciones del sitio quedan bloqueadas.

## Evidencia

- UI: `http://127.0.0.1:3333/#/inbox`, 2 entradas no leídas.
- Click en `Mark read` para una entrada no leída.
- La petición queda pendiente sin `status` ni respuesta.
- Reproducción HTTP equivalente:

```text
curl --max-time 2 -X POST /graphql (mutation inboxMarkRead)
returncode: 28
HTTP=000 TIME=2.006362
0 bytes received
```

- `PRB-534` cubre el estado visual y el retry de la acción, pero no evita el bloqueo del resolver o de la persistencia.

## Comportamiento esperado

`inboxMarkRead` responde en un tiempo acotado, actualiza la entrada y mantiene disponibles las demás operaciones de la UI. Un error de persistencia debe devolver un error GraphQL recuperable, no dejar la petición abierta.

## Criterios de aceptación

- [ ] La mutación `inboxMarkRead` responde con éxito en una base SQLite operativa.
- [ ] La mutación no mantiene bloqueada la API ni otras lecturas/escrituras.
- [ ] Un fallo devuelve un error GraphQL en tiempo acotado.
- [ ] Existe una regresión que cubre la mutación y el síntoma de bloqueo.
- [ ] La prueba de navegador confirma que `Mark read` deja de quedar en `Marking…`.

## Relación

Relacionado con `PRB-534`; este Issue cubre el bloqueo del backend o de la persistencia.
