# Issues: exigir membership del team en mutaciones y recursos dependientes

Created by admin.

## Hallazgo reproducible

Run QA aislado: `20260817T221922Z-e2e`, commit `95b3e6b1051529dc7065ff59a1fb25788a6f267f`, target `http://localhost:3345`, team `PB`.

Con el actor sintético `qa-20260817T221922Z-e2e-viewer` (API key válida, **sin membership** en PB), GraphQL acepta mutaciones de issues sobre recursos PB ajenos:

- `issueCreate(teamId: PB, title: qa-20260817T221922Z-e2e-viewer-issue-created)` devuelve `success: true` y crea `PB-12`.
- `issueUpdate(id: PB-6, description: qa-20260817T221922Z-e2e-viewer-stale-issue-update)` devuelve `success: true` incluso después de revocar una membership sintética del viewer.
- `issueArchive(id: PB-12)` devuelve `success: true`.
- `commentCreate(issueId: PB-6, body: qa-20260817T221922Z-e2e-viewer-comment)` devuelve `success: true` y registra el viewer como actor.
- `issueRelationCreate(issueId: PB-6, relatedIssueId: PB-14, type: RELATED)` devuelve `success: true`.

Los mismos `issueUpdate`, `commentCreate`, `issueArchive` y `issueRelationCreate` aceptaron también actores PB autenticados sobre issues creados por otro actor, sin un chequeo ACL. En contraste, el mismo viewer sin membership recibe correctamente `UNAUTHORIZED` para `projectUpdate`, `milestone*`, `projectArchive` y configuración del team; esto aísla la fuga a las mutaciones del dominio issue.

Evidencia reproducible (sin credenciales): `scratchpad/qa/20260817T221922Z-e2e/evidence/permissions-write.jsonl`, casos `issueCreate`, `issueUpdate-*`, `issueArchive-*`, `commentCreate-protected`, `issueRelationCreate-after-revoke-stale`, `projectUpdate-after-revoke-stale`.

## Comportamiento esperado

Las mutaciones de issues y sus recursos dependientes deben requerir membership en el team del issue (o la política de rol definida para el recurso). Un actor autenticado sin membership debe recibir `UNAUTHORIZED` y no alterar issues, comentarios, relaciones, actividad ni numeración.

La API debe mantener autorización consistente antes y después de revocar una membership; una API key stale no debe conservar capacidad de escritura.

## Criterios de aceptación

- Cubrir GraphQL con owner, member, contributor/agent y outsider sin membership.
- Denegar al outsider `issueCreate`, `issueUpdate`, `issueArchive`, `commentCreate`, `issueRelationCreate` y operaciones equivalentes sobre issues.
- Verificar que el rechazo no deja issue, comentario, relación, actividad ni cambio de numeración.
- Agregar regresiones para revocación de membership y API keys stale.
- Mantener lecturas y validaciones existentes según la política documentada.
