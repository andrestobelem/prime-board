# API keys: create y rotate no asignan el Workspace actual en SQLite

Created by admin.

## Hallazgo

Después de integrar `PRB-472` y `PRB-473`, `apps/server/src/domain/actors.ts` conserva dos caminos sin alcance explícito:

- `createApiKey`/`rotateApiKey` llaman `insertApiKeyMetadata`, que inserta `api_key_team_limits` sin `workspace_id`.
- En una instalación con varios Workspaces, no se crea una fila en `api_key_workspaces` para la key nueva.

El trigger `api_key_team_limits_workspace_required_insert` rechaza un límite sin Workspace. Una key sin grant tampoco puede quedar autorizada para el Workspace actual.

## Comportamiento esperado

Una key creada o rotada desde el Workspace actual debe recibir ese grant y debe guardar sus límites con el mismo `workspace_id`. Las referencias de otro Workspace deben rechazarse sin escribir datos parciales.

## Criterios de aceptación

- [ ] El resolver SQLite propaga el Workspace actual a create y rotate.
- [ ] Los límites se insertan con `workspace_id`.
- [ ] Se crea un grant del Workspace actual sin duplicar keys ni modificar hashes previos.
- [ ] La operación sigue siendo atómica ante un Team de otro Workspace.
- [ ] Hay regresión con dos Workspaces.
