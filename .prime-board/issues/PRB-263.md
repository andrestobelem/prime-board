# Auth: proteger mutations administrativas de team

Created by admin.

## Hallazgo reproducible

Varias mutations administrativas de team solo llaman `requireViewer` y no verifican membership/owner/admin, aunque existe `team_memberships` con roles y `assertTeamOwner`. Un actor autenticado que no pertenece al team puede modificar su workflow: `workflowStateUpdate` con una API key outsider responde `success: true`.

La misma superficie incluye `teamUpdate`, `workflowStateCreate/Delete`, `labelCreate/Update/Delete` y `cycleCreate/Update/Delete`; debe definirse explícitamente qué operaciones puede realizar un owner, un miembro y un admin.

## Evidencia

- `apps/server/src/graphql/resolvers.ts`: esos resolvers usan solo `requireViewer`.
- `apps/server/src/domain/team-memberships.ts`: ya existen `isTeamOwner`, `assertTeamMember` y la protección de membership.
- Reproducción aislada con `createTestApp`: actor agent sin membership cambia el nombre de un workflow state y recibe `success: true`.
- Los tests cubren ownership de memberships, pero no autorización de la configuración del team.

## Comportamiento esperado

Las mutaciones administrativas deben aplicar una política consistente de workspace/team y rechazar actores no autorizados sin modificar datos.

## Criterios de aceptación

- [ ] Se documenta la matriz de permisos para admin, owner, member y actor no miembro.
- [ ] Workflow, labels, ciclos y configuración de team aplican esa matriz.
- [ ] Un actor outsider falla antes de modificar cualquier entidad.
- [ ] Hay pruebas negativas para cada familia de mutation y regresiones para los flujos autorizados.
