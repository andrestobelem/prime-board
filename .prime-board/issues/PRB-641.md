# Migrator: validar CHECKs legacy sin falsos positivos por comentarios

Created by admin.

## Hallazgo

La implementación de PRB-633 usa `normalizedSql(definition).includes(...)` en `checkConstraintProblems`. Un comentario en `sqlite_master` puede contener el fragmento esperado y satisfacer el detector sin imponer el CHECK.

Reproducción: una DB con marker 32/33 y `CHECK (1) /* CHECK (issue_changes = 1 OR slack = 1) */` fue aceptada; después permitió `issue_changes=0` y `slack=0`.

## Comportamiento esperado

La validación debe comprobar la constraint real, no una coincidencia textual en comentarios, strings o SQL no ejecutable. Un CHECK alterado debe fallar antes de aceptar/repetir 0033, sin DDL, datos ni marker parciales.

## Criterios de aceptación

- [ ] Un comentario o literal que contenga el fragmento canónico no satisface la validación.
- [ ] CHECKs canónicos de las tres tablas Views pasan y CHECKs eliminados/alterados fallan.
- [ ] La validación cubre el camino legacy y marker 32/33 idempotente.
- [ ] El fallo deja DDL, datos y `_migrations` sin cambios; el reintento es determinista.
- [ ] La estrategia usa parseo/tokenización segura, definición canónica o probes semánticos; no depende solo de `includes`.
- [ ] Tests sin casts `as` nuevos, typecheck, Prettier y diff-check pasan o documentan brechas.

## Trazabilidad

Hallazgo independiente durante la implementación de PRB-633. Corregir antes de cerrar PRB-633/620/615.
