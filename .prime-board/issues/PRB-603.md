# Integrations: definir contrato OAuth mínimo para agentes

Created by admin.

## Alcance
Definir un contrato OAuth 2.0 mínimo orientado a agentes para PRB-387. Este hijo está separado de Webhooks y no debe ampliar la paridad con Linear ni sustituir la autenticación API-first existente.

- Precisar registro de una aplicación, redirect URIs, actor/Workspace efectivo y scopes mínimos de lectura/escritura.
- Precisar autorización, intercambio de authorization code y refresh token.
- Precisar revocación de grants/tokens y errores estables. Los tokens deben almacenarse hasheados o cifrados fuera de logs, exports y fixtures.
- Reusar los límites de Workspace/Team y la autorización existente. No crear un proveedor externo ni una superficie de Integration Directory.

## Criterios de aceptación propuestos
- [ ] Contrato aprobado para endpoints GraphQL/HTTP, estados y errores de autorización.
- [ ] Scopes se reducen al conjunto permitido por la app y nunca superan los permisos del actor.
- [ ] Authorization codes son de un solo uso y expiran; refresh tokens rotan y una revocación invalida la cadena.
- [ ] Grants/tokens quedan aislados por Workspace y revocados por admin o por el actor dueño.
- [ ] Regresiones para scope insuficiente, code replay, refresh rotation, revocación y aislamiento.
- [ ] Typecheck, Prettier y diff-check pasan sin secretos en evidencia.

## Bloqueo de producto
La documentación vigente de prime-board y ADR-0003/0017 describen API keys como autenticación local-first y dejan OAuth fuera del corte. Antes de implementar se necesita confirmar: ¿se aprueba un OAuth local para agentes dentro del proceso actual, o se debe limitar este ticket a documentar el contrato y dejar la implementación para un despliegue hosteado? Hasta esa respuesta, dejar el hijo en `Needs Info` y no agregar endpoints ni tablas.
